Cross-Environment Runtime Prediction for PostgreSQL Queries

Predicting production query runtime from a developer's machine works within a CPU architecture, and fails across one — and this project shows exactly why, and what fixes it.

13 environments 2 instruction sets 242 measured pairs PostgreSQL 14·15·17·18
Abstract

A query that runs in 400 ms on a developer's laptop may behave very differently on a production server with different memory bandwidth, core count, and instruction set. CETP predicts a PostgreSQL query's production runtime from a plan captured entirely on the developer's own machine — without ever executing the query in production — by measuring each machine's capability directly in SQL and scaling the development-side timing accordingly.

The more significant contribution is a measurement study of where that idea succeeds and where it breaks. Within a single CPU architecture the method is reliably more accurate than assuming production behaves like the developer's machine. Across an architecture boundary — Apple Silicon predicting an x86 server, for instance — it is measurably worse than doing nothing at all, and this project identifies the mechanism, reproduces the failure on four independent machines, and shows that a small number of calibration measurements on the target restores it to parity.

Demonstration

An end-to-end walkthrough of the system: measuring a machine's capability, capturing a development-side query plan, and producing a scaled production runtime prediction with an explicit confidence level.

Result

Three variants sit within six points of the naive baseline. Adding a term for how much parallel speedup each machine actually delivers moves the error from about 67–69% to 30%. Applying that term only to the part of the query plan that runs in parallel, rather than to the whole query, takes it to 22.2%.

The ablation that matters

A single capability scalar with the parallelism term correctly localised scores 22.23%. The full six-axis per-operator model scores 22.41%. The paired difference is −0.17 pp, 95% CI [−0.49, +0.10] — statistically indistinguishable.

The contribution is knowing which part of the plan runs in parallel, not measuring every operator separately. That is a simplification result, and it is reported as one rather than overstated.

Within an architecture the model earns eight points over the baseline, concentrated exactly where capability genuinely differs. Across an architecture boundary it fails, and it failed on all four x86 machines tested independently (66.15 / 67.26 / 69.44 / 72.84%), with the four capability measurements agreeing closely with one another. The failure is systematic, not noise.

Why it fails, which is not what we expected

The obvious explanation is that a different instruction set changes the relative cost of database operations — that a sort is comparatively more expensive on one chip than another. Measured directly, it does not:

arm64 → x86_64, across four independent x86 machines1.20× – 1.27×
Worst pair of capability tiers on a single host1.37×

Crossing the architecture boundary disturbs the mix of operator costs no more than varying resource allocation on one machine does. What breaks instead is the absolute scale: for one measured x86 machine, the capability measurement implied it was 1.667× slower than the development machine; it was actually 1.044× — essentially the same speed. Throughput on a synthetic benchmark operation is not comparable across microarchitectures, which is the same defect carried by a simpler, single-number hardware benchmark this approach replaced, and which produced 324% error when tested laptop-to-cloud. Measuring six operator-level numbers instead of one did not fix it.

Stated honestly

Calibrated, the cross-architecture model reaches parity with simply assuming production behaves like the development machine — 22.32% against 21.74%. It does not clearly beat it. Across an architecture boundary, the capability model contributes little that the calibration measurement alone did not already provide.

The system therefore declines to return an uncalibrated cross-architecture prediction rather than present a number measured to be substantially worse than doing nothing.

How it improves with use

One correction factor is stored per environment pair and refitted as the median of every observation seen for that pair. Accuracy improves for a given pair as measurements accumulate — the calibration curve above is that mechanism in effect.

It does not improve with the number of machines a deployment has previously seen. A correction absorbs one machine's own scale error and says nothing about a different machine. A correction fitted from a single observation is treated as provisional, because in one measured case a single arbitrary calibration query made the prediction measurably worse than no calibration at all.

Negative results

  • Per-operator weighting earns nothing once the parallelism term is present — a paired difference of −0.17 percentage points with a confidence interval crossing zero.
  • A classical analytical cost model is statistically indistinguishable from its simplest component. On an earlier five-machine cloud evaluation, the full analytical model scores 21.61% MAPE and a single compute-ratio term alone scores 20.06% — not significantly different, 95% CI [−0.41, +3.51].
  • Query concurrency cannot be read off a plan. In a leave-one-query-out test, plan-derived features predict a query's concurrency sensitivity worse (mean absolute error 0.191) than simply using the population median (0.167). A population-level default still roughly halves the error under eight concurrent clients (73.79% → 41.81%); knowing the query's own measured sensitivity would reach 6.72%. Concurrency is therefore treated as a caller-supplied input rather than something the system infers.
  • Any model that scales by a single number per machine has a hard ceiling. On the five-machine cloud dataset, true scaling varies roughly 18–43× across different queries run on the same machine, which puts a floor near 59.7% MAPE on any such single-factor predictor regardless of how well it is calibrated. The best measured result with calibration, 55.9%, sits close to that ceiling.

Measurement methodology and its own failure modes

Several published figures in this project were corrected after being caught by the project's own validation checks, each time because of a flaw in the measurement instrument rather than the predictive model. This is reported in detail because it is the finding most likely to generalise beyond this project: capability-probe repeatability is rarely reported in this literature, and here it materially changed the conclusions.

  • An early reliability check validated a capability measurement by how much its individual repetitions varied, when the reported figure is actually a median of those repetitions. Parallel-execution measurements vary substantially run to run even though their median is highly reproducible, so the original check rejected a large share of otherwise valid measurements and silently shifted which machines contributed to the reported averages.
  • An early capability probe ran for too short a duration to amortise one-time startup costs, which on one machine produced a physically impossible result — the machine appeared to run faster under parallel load than a single core alone could support. At a realistic measurement duration the same machine correctly showed parallel execution as slower, because the available cores were being shared.
  • Probing a machine that was not otherwise idle at the time materially changed its measured capability — by more than half, in one measured case — which is why the system now refuses to register a measurement taken under contention.
  • A storage-throughput axis was added to the capability probe specifically to explain a systematic bias in cross-environment predictions. On measurement, it was found to track CPU allocation far more strongly than it tracked available memory — meaning it was not actually isolating storage performance as intended. It is documented as such and excluded from the live prediction model rather than used despite the defect.

Scope and limitations

  1. Not a replacement for a staging-environment benchmark when an SLA decision rests on an absolute runtime figure rather than a relative comparison.
  2. Differing data volumes between development and production are untested. Every environment measured in this evaluation holds identical data, so the data-volume scaling term has never been exercised at a ratio other than one.
  3. No measurement axis isolates storage throughput. This is the diagnosed cause of a residual prediction bias: over-prediction correlates with how much of a query's cost is I/O-bound.
  4. Single-client throughout. Under eight concurrent clients, measured runtime increased by a factor of 8.57× — larger than every other effect measured in this study, and not something the current system predicts on its own.
  5. A bounded workload and environment set. 22 analytical queries at one data scale, one PostgreSQL version per environment, across eight containerised configurations on a single physical host, four independent cloud CI machines, and five historical cloud instances — not a production fleet.
  6. PostgreSQL 14, 15, 17 and 18 were tested and parse correctly across all four. Versions 13 and 16 were not tested and are not claimed.
