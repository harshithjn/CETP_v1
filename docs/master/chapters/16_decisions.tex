\section{Trade-offs that shaped the project}
\begin{enumerate}
\item \textbf{Fidelity vs portability of the signature.} Hardware counters are unavailable on Nitro, so the project measures with the database itself. The price is that the signature depends on PostgreSQL version, build and settings, and cannot be compared across them (\texttt{assert\_comparable}).
\item \textbf{Accuracy vs honesty.} The repository chose to expose negative results (cross-ISA failure, null weighting effect) and to refuse unsafe predictions. This costs a clean headline and gains credibility.
\item \textbf{Ratio vs absolute prediction.} Predicting a ratio keeps the measured dev time as an anchor but requires a dev measurement per query.
\item \textbf{Breadth vs depth.} Four large experiment families (tiers 1--4), JOB and TPC-DS collection code, an extension and a site were built; the headline evidence still rests on five EC2 machines and eight containers.
\item \textbf{Marginal coverage vs per-machine guarantees.} Conformal intervals are valid in aggregate but not for a particular unseen machine (worst 0.78 at nominal 0.90).
\end{enumerate}

\section{What I would change first}
\begin{enumerate}
\item Pass the machine records in \texttt{cetp predict-prod} and add a CLI test (hours).
\item Replace the always-1.0 ``hardware term'' by a Gen-2 ratio or retire the claim; add an accuracy experiment on labelled before/after pairs.
\item Fix the redaction verifier for escape strings and dollar quotes; document that \texttt{full} is pseudonymisation.
\item Regenerate stale warning text from the committed metrics rather than hard-coding numbers.
\item Decide a single source of truth for documentation (restore Markdown or retarget comments).
\end{enumerate}
