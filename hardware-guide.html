CETP · hardware signature

Measuring a production machine

CETP predicts query runtime on a machine it hasn't seen by comparing two numbers between your dev box and the target: a bandwidth score and a compute score. Run this on the production machine once to get both, then paste them into the extension.

Before you start — run this while the machine is otherwise idle. It's a short benchmark: anything else competing for CPU or memory during the ~30–40 seconds it runs will skew the result.
1

Check prerequisites

Three things need to be true on the production machine:

NeededCheck with
Python 3python3 --version
A C compilercc --version
Reachable PostgreSQLpsql -d <yourdb> -c "select 1"

No C compiler on the box? Install one — apt install build-essential on Debian/Ubuntu, yum groupinstall "Development Tools" on RHEL/Amazon Linux. The script compiles a small benchmark on first run; nothing stays installed afterward beyond that one compiler.

2

Get the probe onto the machine

It's two files from the CETP repository that have to sit in the same folder — hw_signature.py and the benchmark it compiles, hw_probe_suite.c. Cloning the repo is the simplest way to get both together correctly: 

# on the production machine
git clone https://github.com/harshithjn/CETP_v1.git
cd CETP_v1/scripts/collection
3

Run it

Give the machine a name you'll recognize later, and point it at any reachable database — it only uses the connection to read one PostgreSQL setting (max_parallel_workers_per_gather), nothing in your schema or data is touched. 

python3 hw_signature.py --machine-id prod-db-1 --db yourdb

It runs seven short benchmarks, one after another, about 3 seconds each:

4

Read off your two numbers

Everything the probe measured is written to models/hardware_signatures.json, under your machine id. Two fields are the ones the extension's Bandwidth and Compute score fields want:

Extension fieldJSON keyWhy this one
Bandwidth (GB/s) probe.mem_bandwidth_gbs_mt Multi-threaded memory bandwidth
Compute score probe.fp_vector_gflops_dop Measured at the degree of parallelism a query can actually reach — not _nproc, which measures every core and overstates what a single query can use

From the sample run above, that's 32.633 and 35.058.

5

Enter them in the extension

Back in VS Code: CETP sidebar → production machine dropdown → Enter manually. Paste the bandwidth and compute values into their fields. Check Save as profile and name it — next time this machine shows up in the dropdown directly, no re-measuring needed.

what you're pasting in
Bandwidth (GB/s) mem_bandwidth_gbs_mt
Compute score fp_vector_gflops_dop
This measures capability, not your query. It does not need to know anything about your schema, your tables, or the queries you plan to run — only how fast the machine itself moves memory and does floating-point work, at the thread count a PostgreSQL query is actually able to reach.
