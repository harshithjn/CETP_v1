# Cross-Environment TPC-H Runtime Prediction (CETP)

CETP predicts how long a TPC-H analytical query will take on a production machine, using only a query plan captured on a development machine and static hardware specifications for both machines. The problem it addresses is that query performance does not transfer across hardware in a simple way: a query that is fast in development can be slow in production, or vice versa, and running a full benchmark suite on every candidate production machine before every deployment is expensive. CETP replaces that benchmark with a prediction, so a CI/CD pipeline can flag a likely SLA violation before a query ever reaches production.

## How it works

CETP decomposes the prediction into two independent parts. The first is the workload cost, extracted from a PostgreSQL `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` plan on the development machine: planner cost, shared buffer hits and reads, and row counts. The second is the hardware signature, a pair of static scores per machine, memory bandwidth and multi-core compute throughput, measured once via short microbenchmarks. A Random Forest classifier uses the workload cost to estimate whether a query is bandwidth-bound, compute-bound, I/O-bound, or mixed, and a set of gradient-boosted quantile regressors combine that classification with the ratio of the two machines' hardware signatures to predict the production runtime's p50, p95, and p99. A hardware-distance check flags predictions made for a production machine that lies far outside the training set, so the system can decline to guess rather than answer confidently on unfamiliar hardware.

## Headline result

**All numbers about this project come from [[`docs/results/CANONICAL.pdf`](docs/results/CANONICAL.pdf)](docs/results/CANONICAL.pdf),
regenerated by `make results`. Do not quote figures from any other file** — several older
reports in `results/` predate the buffer-bug correction or the multi-core compute fix and are
marked superseded where so.

> **Active work (2026-10-13): the predictor described below is being replaced.** The one
> experiment that tested the project's actual claim — predict production runtime from a
> developer's machine, arm64 laptop → x86 EC2 — scored **324% MAPE against 123% for
> assuming production equals development.** It was worse than doing nothing. The
> replacement measures capability by running PostgreSQL's own operators in SQL (so it also
> works on RDS/Aurora, which the C probe could not), scales per operator, and takes the
> plan from production. Design, status and what is still unvalidated:
> **[OPERATOR_MODEL.md](docs/OPERATOR_MODEL.pdf)**.

Across 5 EC2 instance types and 21 TPC-H queries, a single bandwidth ratio is a strong baseline
that no more complex approach beat by a statistically significant margin, with one exception:
once the compute microbenchmark was corrected to measure multi-core throughput instead of
single-core throughput, the physics-based formula using it significantly outperformed the
baseline — **21.61% MAPE vs 23.05%**, improvement +1.44pp, 95% cluster-bootstrap CI
**[0.32, 2.56]**, excluding zero. That figure is computed on the buffer-corrected dataset with
the bottleneck classifier refit inside every cross-validation fold.

**Read that result with its qualification.** Scaling by `1/compute_ratio` alone — no bottleneck
classifier, no roofline weighting, no fitted parameters — scores **20.06% MAPE**, *better* than
the analytical formula's 21.61%. The paired difference is +1.55pp with CI **[-0.41, 3.51]**,
which includes zero, so neither is significantly better than the other. The honest reading is
that **the classifier and the roofline weighting are statistically indistinguishable from their
own simplest component**: the gain over the bandwidth baseline comes from using *compute*
rather than *bandwidth* as the scaling signal, not from the model built on top of it. Any
summary of this project that reports 21.61% without reporting 20.06% beside it is misleading.

The mechanism is confirmed rather than assumed: PostgreSQL chooses parallel plans, so the
compute resource actually consumed is *aggregate* multi-core throughput, which the single-core
probe could not see (r = 0.458, p = 0.037 — `results/fix3_parallelism_mechanism_summary.csv`).

A second finding emerged from the leakage-free re-evaluation: **the analytical formula's accuracy
is protocol-invariant** (21.61% / 21.66% / 21.64% under leave-one-machine-out,
leave-one-query-out, and both at once) **while the learned model's swings from 17.29% to 26.86%
depending purely on whether it has seen the target hardware.** Given every machine, the learned
model is the most accurate approach by a wide margin; given a new machine, it is worse than the
baseline. It interpolates across hardware; it does not extrapolate.

## Using it

```bash
pip install -e .
cetp selftest
```

Then the recommended mode — compare a query before and after a change, which cancels most of
the cross-machine model error:

```bash
cetp regress --before before.json --after after.json --dev c7i --prod c5a --fail-on-regression
```

Full usage, including absolute prediction, plan redaction and registering a new machine, is in
[QUICKSTART.md](docs/QUICKSTART.pdf). What is implemented versus what the design documents claim is
in [IMPLEMENTATION_REFERENCE.md](docs/IMPLEMENTATION_REFERENCE.pdf).

**Before shipping a plan anywhere**, strip its literals — `EXPLAIN` output embeds the query's
values, which on a real database is user data:

```bash
cetp redact plan.json -o plan.redacted.json
```

## Honest status

**The research is sound; treat the product as alpha.** What works: prediction, regression
detection, redaction, machine probing, and a CI action, all exercised by `cetp selftest` and
28 tests. What does not: absolute SLA gating at the accuracy available (54.5% of absolute
BLOCK verdicts in evaluation were false alarms), and any coverage guarantee on hardware
outside the calibration set.

The `models/*.pkl` artifacts that `gate/cetp_gate.py` loads are **stale** — see
[models/MODEL_CARD.md](docs/models/MODEL_CARD.pdf). The installable `cetp` package does not use
them: it ships the analytical formula plus a calibration table, which is both more accurate
out of hull and immune to the staleness.

## Limitations

- **5 machines, 21 queries, SF1, EBS-only, no concurrency.** Nothing here speaks to other
  hardware, instance-local NVMe, other scale factors, or concurrent workloads. The `io`
  bottleneck class reflects buffer-touch patterns under one uniform storage backend, not
  storage diversity.
- **The compute signal is only usable in multi-core form.** Single-core correlates at the
  physically wrong sign (+0.213 vs −0.691) and makes predictions worse.
- **Every p95/p99 result published before 2026-10-12 is contaminated.** Repetition 1 of each
  measurement cell is a cold-cache run — the slowest of 20 in 61 of 105 cells, by up to 8.33x —
  and at n=20 the 95th/99th percentiles sit exactly where that run lands. The p50 headline is
  unaffected (worst-case 0.7%), but tail targets, the quantile calibration table, and any
  p99-based gate result must be regenerated. `make results` now discards the warmup repetition.
- **The shipped gate does not embody the headline finding.** `models/hardware_signature.pkl`
  and `gate/cetp.yml` still carry the old single-core compute scores.
- **The bottleneck classifier is weak and its labels are opinions.** Macro-F1 0.375 on the
  corrected dataset with `io` recall 0.000, against a 0.161 trivial baseline. The 4 class labels
  are 21 hand-assigned judgement calls, and because all six classifier features are
  machine-invariant it is effectively a 21-row lookup table.
- **The three-state gate is not an automatic stop.** It blocks ~8% of pairs with a 54.5%
  false-alarm rate, and its PASS state covered 4 of 840 pairs.

`docs/results/phase7_report.pdf` has the fullest discussion of the earlier negative results, but its
headline conclusion is superseded — see the banner at the top of that file. Everything current
is in [`docs/results/CANONICAL.pdf`](docs/results/CANONICAL.pdf).
