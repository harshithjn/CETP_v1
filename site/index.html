Predicting production query runtime from a developer's machine

It works within a CPU architecture. Across one it is three times worse than guessing — and we can say exactly why.

13 environments 2 instruction sets 242 measured pairs PostgreSQL 14·15·17·18

A query takes 400 ms on your laptop. Production runs on different hardware. Will it meet the SLA? CETP answers from a plan captured on your own machine — and, more usefully, establishes where that whole approach stops working.

Result

Three variants sit at or above the naive baseline. Adding a term for how much parallel speedup each machine actually delivers moves the error from 76% to 30%. Applying that term only to the part of the plan below a Gather, rather than to the whole query, takes it to 24.6%.

The ablation that matters

A single capability scalar with the parallelism term correctly localised scores 24.58%. The full six-axis per-operator model scores 24.95%. The paired difference is −0.37 pp, CI [−0.84, +0.01] — indistinguishable.

So the contribution is knowing which part of the plan runs in parallel, not measuring each operator separately. That is a simplification result, and it is reported as one.

Within an architecture the model earns eight points over the baseline, concentrated exactly where capability genuinely differs — on the most constrained machine, 62.58% drops to 23.47%. Across an architecture boundary it fails, and it failed on all four x86 machines tested (66.15 / 67.26 / 69.44 / 72.84%), with the four capability signatures agreeing within 5% of each other. Systematic, not noise.

Why it fails, which is not what we expected

The obvious explanation is that a different instruction set changes the relative cost of operations — that a sort is comparatively dearer on one chip than another. Measured directly, it does not:

Operator-mix perturbationSpread
arm64 → x86_64, different vendor and core count1.365×
Worst pair of containers on a single host1.371×

Crossing the architecture boundary disturbs the operator mix no more than changing a CPU quota on one machine does. What breaks is the absolute scale: the probe reported the x86 machine 1.667× slower than the laptop when it was actually 1.044× — the same speed. Tuples per second on a synthetic operation is not comparable across microarchitectures.

That is precisely the defect of the floating-point benchmark this replaced, which scored 324% error laptop-to-cloud. Swapping one architecture-sensitive number for six did not fix it.

Calibrated, the cross-architecture model reaches parity with assuming production matches your machine — 23.38% against 21.41%. It does not beat it. On that pair the capability model contributes nothing the calibration did not.

The tool therefore refuses an uncalibrated cross-architecture prediction rather than returning a number measured to be three times worse than doing nothing.

How it improves with use

One correction is stored per environment pair and refitted as the median of every observation seen. Accuracy improves for that pair as measurements accumulate — the curve above is that mechanism.

It does not improve with the number of machines in the registry. A correction absorbs one machine's scale error and says nothing about another. A correction from a single observation is marked provisional, because one arbitrary measurement scored worse than no calibration at all (19.51% against 15.84%).

Negative results

  • Per-operator weighting earns nothing once the parallelism term is present — −0.37 pp, CI crossing zero.
  • The classic roofline model is indistinguishable from its simplest part. On the original five-machine cloud dataset, an analytical roofline scores 21.61% and 1/compute_ratio alone scores 20.06% — better, not significantly.
  • Concurrency cannot be read off a plan. Leave-one-query-out, plan features predict the elasticity exponent at MAE 0.191 against 0.167 for simply using the median. A global default halves the error at eight clients (73.79% → 41.81%); the query's own value would reach 6.72%. So load is an input the caller supplies.
  • Scalar capability models have a hard ceiling. On the cloud dataset the true scaling varies 18–43× across queries on one machine, putting a floor of 59.7% on any per-machine single-factor predictor. The best measurement reached 55.88% — already at it.

Measurement hygiene

Published numbers here were corrected four times, every time because of the instrument rather than the model. This is reported because it is the finding most likely to generalise: nobody in this literature reports probe repeatability, and here it changed the conclusions.

  • The reliability gate checked run-to-run spread while the reported figure is a median. Parallel measurements jitter badly per run (cv 0.587) but their median reproduces to 3%. The gate rejected half the good machines, shifting the population and moving headline numbers by 5–15 points.
  • Probe runs were twenty times too short. An 18 ms parallel scan is mostly worker startup; one machine reported an impossible 1.81× speedup on a single CPU. At realistic size it reports 0.808× — correctly slower, because three workers share one core.
  • Probing a machine that was not idle moved its measured speedup from 2.47× to 1.14×.
  • A storage axis was built and does not measure storage: it tracks CPU quota (+0.762) over memory (+0.548). Kept, documented as such, unused by the model.

Using it

pip install -e .
cetp selftest

# measure each machine once — SQL only, so this works on RDS and Aurora.
# run it on an IDLE machine: under load it measures contention, not capability.
python3 scripts/collection/operator_probe.py --machine-id dev-laptop --db mydb
python3 scripts/collection/operator_probe.py --machine-id prod-db   --db mydb \
    --host prod.example.com --user readonly

# predict. production is EXPLAINed, never executed.
python3 scripts/collection/predict_prod.py --query-file q.sql \
    --dev dev-laptop --prod prod-db --prod-host prod.example.com \
    --prod-db mydb --prod-user readonly --dev-db mydb --sla-ms 2000

The most reliable mode is comparing the same query before and after a change: the hardware term appears in numerator and denominator and largely cancels, so the answer is essentially your measured dev-side ratio. That is what belongs in CI.

Boundaries

  1. Not a replacement for a staging benchmark when an SLA decision rests on an absolute number.
  2. Differing data volumes are untested. Every environment measured holds identical data, so the cardinality term has never run at a ratio other than one.
  3. No axis measures storage. It is the diagnosed residual: over-prediction correlates with each query's I/O fraction at Spearman r = +0.302.
  4. Single client throughout. At eight clients runtime moved 8.57× — larger than every other effect measured here.
  5. 22 TPC-H queries, one scale factor, one engine version per environment. Environments are eight containers on one arm64 host, four AMD CI runners, and five historical EC2 instances — not a production fleet.
  6. PostgreSQL 14, 15, 17 and 18 are tested. 13 and 16 are not, and are not claimed.
