Cross-environment runtime prediction for PostgreSQL

Can a developer's machine predict how long a query will take in production? Within one CPU architecture, yes — about 29% error against 37% for guessing. Across architectures the same method is three times worse than guessing, and this is the measurement of why.

The useful finding is not a better predictor. It is that encoding hardware capability as a measured number works within a CPU architecture and fails across one — and that one cheap correction fixes it.

What the system does

You capture a query plan on your own machine. The tool measures each machine's capability by running PostgreSQL's own operators in SQL, works out how your plan's time is distributed across those operators, and scales it:

T_prod  =  T_dev  ×  Σ  w_op · rate_dev(op)·s_dev / (rate_prod(op)·s_prod)  ×  calibration  ×  N^e

w_op is where your machine actually spent wall time, s is the parallel speedup each machine grants, N^e is concurrency, and calibration is learned from queries measured on the target.

Why the capability probe is SQL

It measures six things by running them: sequential scan, hash join, sort, hash aggregation, indexed nested loop, and the parallel speedup the machine actually delivers. Being only SQL, it runs on managed PostgreSQL — RDS, Aurora, Cloud SQL — where you have no shell and cannot compile a benchmark. The predecessor was a C program measuring floating-point throughput, which no database query issues.

The cause, and it is not what we expected

We expected the architecture boundary to change the relative cost of operators — that a sort might be comparatively dearer on one chip than another. Measured directly, it does not. arm64 → x86 perturbs the operator mix by 1.365×; the worst pair of containers on one host perturbs it by 1.371×.

What breaks is the absolute scale. The probe reported the x86 machine 1.667× slower than the laptop; it was actually 1.044× — essentially the same speed. Tuples per second on a synthetic operator is simply not comparable across microarchitectures. That is the same defect as the floating-point signature it replaced: swapping one architecture-sensitive number for five did not fix it.

Honest limit: calibrated, the cross-architecture model reaches parity with simply assuming production equals development (23.4% against 21.4%). It does not beat it. On that pair the capability model contributes nothing the calibration did not.

How it improves with use

Accuracy improves per environment pair as observations accumulate — a correction is stored for each (development, production) pair and refitted as the median of everything seen. One pair went from 72.84% to 23.38% on five observations.

What it does not do. Accuracy does not improve with the number of machines in the registry. A correction learned for one production machine says nothing about another, because it absorbs that machine's specific scale error. Pooling across machines has not been demonstrated here, and the code says so rather than implying otherwise.

A correction from one or two queries is marked provisional: a single arbitrary observation measured worse than no calibration at all (19.51% against 15.84%). Three is where it became reliably better.

Negative results worth more than the positive one

  • Per-operator weighting earns nothing. One capability scalar, with the parallelism correction applied to the right part of the plan, scores 24.58% against the full per-operator model's 24.95% — a difference of −0.08 pp, confidence interval [−0.73, +0.44]. The complexity is not justified by the evidence.
  • Parallelism is the whole result. Remove that term and the model is level with doing nothing (76.2% against 72.5%). Localising it to the nodes below a Gather — rather than applying it to the whole query — is worth +6.91 pp, CI [+0.95, +14.73].
  • The classic roofline model is indistinguishable from its simplest part. On the original 5-machine cloud dataset, an analytical roofline scores 21.61% and 1/compute_ratio alone scores 20.06% — better, with the difference not significant.
  • Concurrency cannot be predicted from a plan. Leave-one-query-out, plan features predict the elasticity exponent at MAE 0.191 against 0.167 for simply using the median. A global default halves the error at 8 clients (73.8% → 41.8%), but knowing the query's own value would reach 6.7%. So load is an input the caller must supply.
  • Measuring hardware capability as a scalar has a hard ceiling. On the cloud dataset the scaling factor varies 18–43× across queries on one machine, which puts a floor of 59.7% on any per-machine single-factor predictor. The best measurement reached 55.88% — already at the floor.

Measurement hygiene, which turned out to decide the answers

Published numbers in this project were corrected four times, every time because of the instrument rather than the model:

  • The reliability gate checked run-to-run spread, but the reported figure is a median. Parallel measurements jitter wildly per run (cv 0.587) while their median reproduces to 3%. The old gate rejected half the good machines, which shifted the population and moved headline numbers by 5–15 points. It now checks the bootstrap standard error of the median.
  • Probe runs were 20× too short: a parallel scan finished in 18 ms, so worker startup dominated and one machine reported an impossible 1.81× speedup on a single CPU. At realistic size the same machine reports 0.78× — parallelism correctly making it slower when three workers share one core.
  • Probing a machine that was not idle moved its measured speedup from 2.47× to 1.14×. Any capability probe taken under load is discarded.
  • A storage axis was built, and it does not measure storage: it tracks CPU quota (+0.762) over memory (+0.548). It is kept, documented as such, and unused by the model.

This is reported because it is the finding most likely to generalise: nobody in this literature reports probe repeatability, and here it changed the conclusions.

Try it

pip install -e .
cetp selftest

# register both machines — SQL only, so this works on RDS/Aurora.
# run it on an IDLE machine: under load it measures contention, not capability.
python scripts/collection/operator_probe.py --machine-id dev-laptop --db mydb
python scripts/collection/operator_probe.py --machine-id prod-db   --db mydb \
    --host prod.example.com --user readonly

# predict. production is only EXPLAINed, never executed.
python scripts/collection/predict_prod.py --query-file q.sql \
    --dev dev-laptop --prod prod-db --prod-host prod.example.com \
    --prod-db mydb --prod-user readonly --dev-db mydb --sla-ms 2000

Across architectures an uncalibrated prediction is refused, not warned about — it is the one configuration measured to be far worse than doing nothing. Measure three to five queries on the target and the refusal lifts.

What this is not

  • Not a replacement for a staging benchmark when an SLA decision rests on an absolute number.
  • Not validated for differing data volumes. Every experiment has identical data on both sides, so the data-size term has never been exercised at anything but a ratio of one.
  • Not tested on non-AMD x86, nor on a non-CI host. Four x86 machines, two CPU models, all AMD EPYC on one cloud.
  • Single client throughout. Concurrency is an input you supply, and at eight clients it moved runtime 8.57× — larger than every other effect measured here.
  • 22 TPC-H queries at one scale factor, one engine version.
