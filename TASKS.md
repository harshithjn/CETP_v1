### What the audit found that was not on the original list

- [x] **A cold-cache warmup defect.** Repetition 1 of every cell is a cold run — the slowest of
      20 in **61 of 105 cells**, by up to **8.33x**. `make results` now discards it.
      **p50 is unaffected** (worst case 0.7%), so the headline stands. But **p95 inflated >5% in
      17/105 cells and p99 in 46/105, up to 6.92x** — so *every p95/p99 result published before
      this audit is contaminated*, and this is the most likely cause of the reported quantile
      under-coverage (80.7% at nominal 95%). The models were partly being asked to predict a
      measurement artifact.
- [x] **Classifier features are machine-invariant.** On the corrected dataset all six
      (`cost`, `shared_hit`, `shared_read`, `total_buffers`, `io_ratio`, `rows`) are *identical
      across all five machines* for a given query. Two consequences: (a) the LOMO leak was real
      but structurally harmless, since held-out rows duplicate training rows; (b) six of the
      thirteen learned-model features are **a one-hot encoding of `query_id` in disguise**, so
      under LOMO the GBR can memorise per-query scaling.
- [x] **Three protocols now reported, and the contrast is a result in itself.** The analytical
      formula is protocol-invariant (**21.61 / 21.66 / 21.64%** for LOMO / LOQO / LOMQO) while
      the learned model swings **17.29% → 26.86%** purely on whether it has seen the target
      hardware. Given every machine it is the most accurate approach by a wide margin; given a
      new machine it is worse than the baseline. This is the interpolation-not-extrapolation
      finding, now measured directly rather than inferred from one fold.
- [x] **The analytical gain is localised.** It comes almost entirely from `compute`-labelled
      queries (22.63% → 17.55%) and `mixed` (23.04% → 21.58%). On `bandwidth` and `io` queries
      it is identical to the baseline *by construction*, because the io weight is applied to
      `1/bandwidth_ratio`.
- [x] **RESOLVED 2026-10-13: the shipped models were stale three ways** — trained on the
      buffer-bug dataset (disagreeing with a correct classifier on **20 of 105 cells**,
      probability deltas up to 0.997), pickled with scikit-learn 1.6.1 against a 1.8.0 pin, and
      `hardware_signature.pkl`/`gate/cetp.yml` carrying the **single-core** compute signal.
      All three are fixed: retrained on `data/corrected/tpch_dataset_corrected_v2.csv` under
      sklearn 1.8.0, and both the signature and `gate/cetp.yml` now carry the multi-core
      aggregate, so **the deployed gate implements the headline finding**. The compute score is
      obtained by running `scripts/collection/hw_signature.py` (surfaced in the extension as
      `cetp.measureMachine`), which was the open product decision. Provenance in
      `models/PROVENANCE.json`; previous artifacts in `models_backup/`.
      `canonical_evaluation.py` now *verifies* this consistency at runtime rather than
      asserting it, so the claim cannot go stale again.
- [x] **RESOLVED 2026-10-13: experiments are separated from releases.** `phase5_classifier.py`
      and `phase6_scaling_regressor.py` now write to `models_candidate/`, and promotion is the

## Tier 1 — Make the method defensible. ✅ COMPLETE (2026-10-12)

Full results: **[TIER1_RESULTS.md](TIER1_RESULTS.md)**. Headline: the method's central structure
does not hold up, and Tier 1 found exactly why — the two-axis hardware signature is one axis
measured twice (r = +0.958, PCA 97.9%/2.1%), which forces the bottleneck taxonomy to be
inert.

- [x] **17. Elasticity rig built** — `scripts/collection/elasticity_probe.py`, 3 axes
      (parallel DOP, work_mem, bandwidth antagonist), 338 measurements,
      `results/elasticity_raw.csv`. Also wrote `membw_antagonist.c`. The 8-thread antagonist
      level was collected and **discarded**: on an 8-core machine it starves PostgreSQL of CPU
      rather than contending for bandwidth (q1 ran 526,827 ms against a ~4,000 ms baseline).
      No affinity control on macOS, so `e_bw` is a two-point slope and indicative only.
- [x] **18. Elasticity replaces the hand labels — hypothesis REFUTED.** The measured
      elasticities contradict the labels (compute- and bandwidth-labelled queries have
      *identical* measured compute sensitivity; `mixed` has the highest bandwidth sensitivity),
      but as weights they score 21.76% — behind the hand labels (21.62%) and a flat uniform
      split (21.55%). Better description, no predictive gain.
- [x] **19. Classifier ablation — the classifier is decorative.** Uniform 0.25 weights
      (21.55%) beat the learned classifier (21.61%). `cmp_only` (20.06%) beats everything.
      Oracle bound 17.07%.
- [x] **20. Conformalized quantile regression, group-calibrated** — delivers 97.0% empirical at
      nominal 95% where the shipped GBR gives 84.6%. Costs ~29% wider intervals.
- [x] **21. Weighted conformal under covariate shift** — implemented; **no measurable gain**.
      With 4 calibration machines there are only 4 distinct weights.
- [x] **22. Derive the confidence threshold — CANNOT BE DONE at n=5.** The score takes one
      value per machine: 6 operating points total, and risk does not fall monotonically as
      coverage drops. Separately: the gate helps the learned model (1.71x error ratio), is
      **inverted** for the analytical formula (0.86x) and flat for `cmp_only` (1.00x) — it
      guards the one component the project does not recommend shipping.
- [x] **23. Three-state gate — RETIRED.** A conformal gate's PASS state delivers its guarantee
      (1.37% breach at nominal ≤5%) where the shipped gate's does not (6.24%), but **BLOCK is
      empty at every SLA tested**: these interval widths can guarantee "safe" and never
      "unsafe". Ship a two-state guaranteed-pass / defer gate.
- [x] **24. Log-space modelling** — better point estimates, *worse* intervals (72.9% at nominal
      95%) because a global residual quantile does not adapt. Use log space for points,
      conformal for bounds.
- [x] **25. Plan-structure features — CLEAR POSITIVE RESULT.** 50 features from
      `extract_plan_features_v2.py`. On unseen queries (LOQO, the honest test): 17.29% → **13.29%**,
      a 23% relative gain. And **the shipped 13-feature set is worse than two hardware ratios
      alone** (17.29% vs 16.10%). Invest here; delete the classifier.
- [x] **26. "Are two scalars enough?" — you do not have two.** r = +0.958 between the axes,
      97.9% of variance on one principal component, and that axis is largely core count
      (r = +0.841). Unanswerable on this data. `hw_probe_suite.c` (7 axes) is written and
      validated (its vector-FP figure matches `compute_probe.c` to 1.8%; latency hierarchy
      monotonic) but has run on one machine only.
- [x] **27. arm64 laptop as dev — IT FAILS.** 324% MAPE laptop→cloud against 20% within the
      EC2 hull, and `naive` (prod = laptop) beats it at 123%. Root cause found: the compute
      score is probed at `nproc` but a query can use only
      `1 + max_parallel_workers_per_gather = 3`; DOP-matching halves the error.
      **This impugns the headline result**, which rests on a score probed at `nproc`.
- [x] **28. Q15 fixed.** CTE with `NOT MATERIALIZED` reproduces the spec view form's plan
      *exactly* (same node count, depth and total cost to the cent); plain `MATERIALIZED` gives
      a different, ~2x cheaper plan and would have been the wrong substitution.
      `results/q15_resolution.md`. The workload is 22 queries.
- [x] **29. Measurement noise propagated** — floor is **0.60%** relative SE against ~20% model
      error. **Noise is not the binding constraint.**

### Incidental obstacles worth remembering

- `pg_dump` must be >= the server version, and a **PG15 dump cannot be restored into PG14 at
  all** (downgrades unsupported) — which is why every version is loaded from source CSVs.
- **PostgreSQL 17+ on macOS refuses to start with an unset locale** ("postmaster became
  multithreaded during startup"). `LC_ALL=C` fixes it, and setting it uniformly keeps
  collation — and therefore sort costs — identical across versions.
- macOS ships **bash 3.2**: no associative arrays.

## Tier 3 — Research. ✅ COMPLETE (2026-10-12)

Full results: **[TIER3_RESULTS.md](TIER3_RESULTS.md)**. Related work first, per item 44 — and
it changed the framing before any experiment ran: **[RELATED_WORK.md](RELATED_WORK.md)**.

Headline: three of the four research angles do not survive contact with the data, and knowing
which is the contribution. Every one fails for the same reason — five machines and a
one-dimensional hardware signature — which makes that a finding supported from five
independent directions rather than a limitation.

- [x] **39. N1 plan drift — IS the headline (corrected 2026-10-13).** A causal
      decomposition with forced plans (`results/tier4_plan_drift_causal.md`) finds the pure
      plan effect is **1.673x** against **1.145x** for settings — **70.5%** of the runtime
      difference — over 30 verified cells. That supersedes the observational ~16% below, which
      was diluted by averaging over pairs where the plan never changed. Caveat: forcing
      verified on only 41% of differing-plan cells, and the failures are not random.
      Superseded detail from the first pass: Measured on one machine varying only the
      planner's hardware *beliefs*, so capability is constant and drift is isolated with no
      confound. **20/22 queries change plan** (median 3, max 6), driven most by core count
      (55% of queries when `max_parallel_workers_per_gather` goes 2→8). But it is the **smaller
      term**: same-plan pairs swing runtime 2.16x, different-plan pairs 2.49x, so only **~16%**
      of variation is plan change (p = 1.7e-3). And the correlation with error is
      **inverted** (r = −0.551, p = 0.010): plan-volatile queries are predicted *better*,
      because volatility marks parallelisability. Survives as: drift is pervasive, core count
      drives it, and **plan volatility is a usable dev-side signal for which queries transfer**.
- [x] **40. N2 elasticity as a descriptor — refuted in Tier 1.** Better description of the
      queries, no predictive gain (21.76% vs 21.55% for a flat uniform split).
- [x] **41. N3 budgeted cold start — done, and it inverts the premise.** **One well-chosen
      query (13.20%) beats twelve random ones (13.45%).** Calibrating from a single *random*
      query makes things **worse** than not calibrating (19.51% vs 15.84%), which the old
      arbitrary-12 loop could never have detected. `elasticity` and `dopt` degrade as k grows
      because both chase extremes; for estimating one scalar you want representative queries.
- [x] **42. N4 conformal risk control — machinery works, guarantee voids.** **16 of 18
      configurations exceed their stated risk budget on the held-out machine**, worst fold
      26.8% against a 5% budget. Not a bug: CRC assumes exchangeability, and a held-out machine
      is not exchangeable. Tier 1 found the same from the coverage side. Keep the framing
      (a *derived* threshold beats the hand-set 0.6), report the budget as aspirational.
- [ ] **43. N5 learned hardware embeddings — BLOCKED**, needs 30+ machines. Tier 1 already
      answered the underlying question more cheaply: with r = +0.958 between the two axes and
      97.9% of variance on one component, there is no second dimension to embed.
- [x] **44. Related work written before the experiments** — and it changed the framing, exactly
      as the item predicted.
- [x] **45. Citations verified — four of eight were wrong or incomplete.** "QPPNet" is not the
      paper's own name; the covariate-shift conformal paper is Tibshirani, **Barber, Candès &
      Ramdas**; Ganapathi's title and Neo's eight-author list were off. Roofline's volume/issue
      still needs confirming.
- [x] **46. Differentiator stated — and narrowed.** The list missed the closest prior work:
      **COSTREAM (Heinrich, Binnig, Kornmayer & Luthra, ICDE 2024)**, a learned cost model
      taking hardware as input. It *does* evaluate extrapolation beyond its training range, so
      **"no prior work tests cross-hardware extrapolation" must not be claimed.** Only three
      things survive as novel: relational OLAP rather than streaming (where a plan enumerator
      exists at all), **latency percentiles** as the decision variable rather than a point cost
      with q-error percentiles, and **abstention**. Note Binnig co-authors both nearest papers.

### What Tier 3 changes about the project

- [ ] **Write a measurement study, not a better predictor.** Target **aiDM or DBTest at
      SIGMOD**. A VLDB full paper claiming state-of-the-art is not supportable by a 5-machine
      evaluation and should not be attempted.
- [ ] **Lead with the critique that generalises**: encoding hardware capability as a scalar

      none discusses; and two correlated probes are not two dimensions. COSTREAM uses four
      hardware features and never tests their independence either.

## Tier 6 — Make the actual thesis work: per-operator cross-environment prediction (2026-10-13)

Context: the project's stated goal is "predict production runtime from the developer's
machine", and the one experiment that tested exactly that scored **324% MAPE (153% after
the DOP fix) against 123% for assuming production equals development**. The model was worse
than doing nothing. Design and status: **[OPERATOR_MODEL.md](OPERATOR_MODEL.md)**.

- [x] **Move 1 — operator capability probe, in SQL.** `scripts/collection/operator_probe.py`.
      Six axes (seqscan, hashjoin, sort, hashagg, nestloop, parallel_seqscan). Replaces
      FP-vector GFLOPS, which measured a quantity TPC-H never issues. Being SQL it runs on
      RDS/Aurora/Cloud SQL, which the C probe could not. The axes decouple: work_mem
      64MB->1MB left seqscan at 1.049x and cut hashjoin to 0.580x, a 1.81x spread no single
      scalar can express.
- [x] **Two guards, both of which caught real faults.** Operator verification caught the
      nestloop probe silently measuring a hash semi-join (5.2M reported against 1.25M
      true). The repeatability gate (`MAX_CV = 0.15`) caught probing under load: running
      the probe while the container sweep ran moved seqscan's cv from 0.008 to 0.337 and
      the parallel speedup from 2.47x to 1.14x. Unreliable records are refused by
      `cetp.cross_env.load_rates`.
- [x] **Move 2 — per-operator scaling.** `cetp/plan_nodes.py` + `cetp/operator_model.py`.
      Weighted per-axis capability ratio. Three corrections that are easy to get wrong:
      `Actual Total Time` is cumulative (subtract children) AND per-loop (multiply by
      `Actual Loops`); the model predicts a *ratio* rather than summing scaled node times,
      because under a Gather the self-times sum to CPU time (measured 2.85x wall on q19);
      and the parallelism correction keys on **under_gather**, not `Parallel Aware`.
- [x] **The parallelism axis was missing and it mattered.** Found by running the model, not
      by reading it. Predicting the 1-CPU container from the 8-core host, TPC-H q19, true
      ratio 3.011x: serial axes only **1.080x (64.1% error)**; parallelism keyed on
      `Parallel Aware` **1.493x (50.4%)**; keyed on `under_gather` **2.664x (11.5%)**.
      This is the `nproc`-vs-achievable-DOP bug in a new form.
- [x] **Move 3 — the plan comes from production.** `scripts/collection/predict_prod.py`.

- [x] **Move 4 — few-shot calibration.** `fit_calibration` (median, not mean) and

      not calibrating.
- [x] **Orthogonal capability grid RUN.** `container_grid.py` reduced to 4 CPU x 2 memory

- [x] **Probe measurement duration was a real bug, found by running it.** At 400k rows the

- [x] **Cardinality term was wrong and is fixed.** The first implementation used

- [x] **THE THESIS IS ACHIEVED.** Laptop (M1, arm64) -> 6 container production machines,

- [x] **Move 4 (few-shot) is MODEST, not essential.** 28.54% -> 23.25-23.37% at k=5-8. And

- [x] **Move 2 SPLIT by ablation, and this is the key scientific result.**
      `scalar_localized_par` -- ONE serial capability scalar, with the parallelism
      correction applied only to the plan's parallel wall-time share -- scores **22.23%**
      against the full per-operator model's **22.30%**: delta **-0.08pp, CI [-0.73, +0.44],

      whole-query instead of localising it costs **+6.91pp, CI [+0.95, +14.73],
      SIGNIFICANT.**

      Per-operator RATE weighting adds nothing measurable, and the dispersion table says
      why: serial axes span only 1.02-1.13x across the grid while parallel speedup spans
      3.66x. This is a SIMPLIFICATION result -- one serial scalar + one parallel speedup +
      the plan's parallel/serial split is sufficient on this evidence.
- [x] **The zero-shot residual is DIAGNOSED.** Systematic over-prediction (mean signed error
      +0.181, per machine +0.015 to +0.359). The probe is cache-resident (~120 MB tables vs
      a 128 MB buffer pool) while TPC-H reads ~850 MB past it. Over-prediction correlates
      with each query's I/O fraction (Spearman r = +0.302).
- [ ] **ADD AN I/O AXIS TO THE PROBE.** Highest-value change remaining: nothing in the
      signature measures read throughput past the buffer pool. Needs a probe table several
      times `shared_buffers`.
- [x] **Second ISA OBTAINED, and the result is NEGATIVE** -- the most important finding of
      this round (`results/cross_isa_operator_rates.md`). An x86_64 AMD EPYC 9V74 runner was
      probed through `.github/workflows/x86-operator-probe.yml` (reps=9, record passed the
      repeatability gate). Crossing **arm64 -> x86_64 perturbs the operator mix by 1.365x**;
      the worst pair **within** the arm64 container grid perturbs it by **1.371x**. The ISA
      boundary is no harder on operator mix than a CPU quota change on one machine.
      **This refutes the stated motivation for per-operator capability modelling**, and means
      the 59.7% cross-ISA floor is NOT caused by operator-mix divergence. Combined with the
      grid ablation (-0.08pp, CI [-0.73, +0.44]), two independent experiments now agree:
      per-operator RATES are not the useful part; the parallelism term and its
      plan-structure localisation are.
- [x] **CROSS-ISA PREDICTION MEASURED, and it fails without calibration**
      (`results/cross_isa_prediction.md`). 176 pairs over 8 production machines, one a real
      x86_64 AMD EPYC 9V74 collected through GitHub Actions.
      **Same ISA (7 arm64 cells, 154 pairs): operator 29.31% vs naive 37.39% -- the model
      works. Cross ISA (1 x86 cell, 22 pairs): operator 72.84% vs naive 21.41% -- 3.4x WORSE
      than doing nothing.**
      Mechanism: the probe says x86 is 1.667x slower than the M1; it is actually 1.044x. Not
      operator-mix divergence (refuted above) but the ABSOLUTE SCALE -- tuples/s on a
      synthetic operator is not comparable across microarchitectures. The same defect as the
      original FP-GFLOPS signature; five architecture-sensitive scalars instead of one did
      not fix it.
      **Calibration repairs it and is mandatory across an ISA:** k=5 takes the x86 cell to
      23.38% (floor 16.75%) -- but only to PARITY with naive's 21.41%, not past it.
